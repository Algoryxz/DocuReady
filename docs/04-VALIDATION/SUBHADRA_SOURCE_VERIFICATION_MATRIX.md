## 2. Parameter-level verification matrix

Status vocabulary:
- **VERIFIED** — the cited official source expressly establishes the requirement or rule.
- **PARTIALLY VERIFIED** — the source establishes part of the proposition, but scope or operational interpretation remains unresolved.
- **UNVERIFIED** — no adequate authoritative evidence has been established for the specific proposition.
- **NOT AUTOMATABLE** — legal requirement may be verified, but the current DocuReady inputs/integrations cannot safely determine it.
- **DEFERRED** — deliberately not implemented pending trusted evidence, product-owner approval, or a suitable primitive.

## 3. Specific rule-level review findings

### RULE-SUB-DOC-01 — Aadhaar document slot

- **Legal fact:** Aadhaar card/Aadhaar number in the applicant's own name is a verified scheme requirement (Gazette §5(a)(i); Guidelines §7(a)(i); SOP §2(f)).
- **Current primitive contract checked on this branch:** `eval_require_document()` returns `Raw.DOC_ABSENT` when the requested slot is absent. The V2 resolver handles `Raw.DOC_ABSENT` before severity-cap processing and returns `Status.MISSING` / `ReasonCode.DOC_ABSENT`. Therefore `max_severity: REVIEW` cannot convert this outcome to REVIEW; changing the cap is not a valid correction. The current `ReasonCode` enum also has no `DIGITAL_EVIDENCE_NOT_SUPPLIED` value.
- **Implementation-compatible proposal for the next approved pack revision:** Keep `doc_slots.aadhaar_card.required: false` for the optional DocuReady digital-upload slot and do not apply `require_document` to that optional scan. Remove the pack-specific `RULE-SUB-DOC-01` missing-upload rule rather than trying to severity-cap `Raw.DOC_ABSENT`. No new raw outcome or reason code is proposed.
- **Result when the digital scan is absent:** No standalone missing-Aadhaar-upload finding is emitted. Rules that genuinely depend on Aadhaar fields must abstain using the existing `Raw.INDETERMINATE` + `EvidenceState.UNCERTAIN` contract and resolve to `Status.REVIEW` / `ReasonCode.INSUFFICIENT_DATA`. For this pack, `age_on` already abstains when DOB evidence is unavailable; `match_across` abstains when too few fields are extracted; `field_present` must be corrected as specified below. With these dependent-rule behaviours, the expected packet-level result is `NEEDS_CHECKS`, not `NOT_READY` solely because the optional scan was not uploaded.
- **Unreadable/corrupted scan:** Keep the existing indeterminate/uncertain evidence route, resolved to REVIEW / INSUFFICIENT_DATA; do not emit a statutory FAIL or missing-document verdict.
- **Applicant-facing explanation:** If Product chooses to show a reminder that the optional digital copy was not uploaded, it must be a non-finding upload/help-text state outside the rule resolver. It must not invent a statutory status or a new reason code.
- **Physical possession remains distinct:** Absence of a DocuReady scan cannot establish that the applicant lacks physical Aadhaar/Aadhaar number. Conversely, the optional upload is not evidence that e-KYC or Aadhaar-mobile linkage has been completed.
- **Hold:** These are proposed matrix semantics only. Do not modify the current pack, primitive, resolver, or tests until Akriti explicitly agrees to the matrix and the implementation changes are authorized.

### RULE-SUB-FLD-01 — applicant-name field presence

- **Current primitive contract checked on this branch:** In `eval_field_present()`, a missing source document or any non-`VALID` source document is currently skipped with `continue`. If no extracted field is collected, the primitive then returns `Raw.SATISFIED` with `EvidenceState.UNCERTAIN` and the message that the mandatory field “is present and non-empty.” The resolver downgrades that apparent satisfaction to REVIEW / CANNOT_CONFIRM, but the raw result and primitive message remain misleading.
- **Exact proposed behaviour for an absent source:** Return `Raw.INDETERMINATE`, `EvidenceState.UNCERTAIN`, identify the expected source document in `documents_involved`, attach no fabricated field evidence, and use a message such as: “Source document 'AADHAAR' is not present in the packet; applicant_name cannot be assessed.” The existing resolver must produce `Status.REVIEW` / `ReasonCode.INSUFFICIENT_DATA`.
- **Exact proposed behaviour for a source marked MISSING:** Treat it like an absent source: `Raw.INDETERMINATE` / `EvidenceState.UNCERTAIN` / REVIEW / INSUFFICIENT_DATA; no `Raw.SATISFIED`.
- **Exact proposed behaviour for unreadable/corrupted source:** Return `Raw.INDETERMINATE` / `EvidenceState.UNCERTAIN`, with an explicit unreadable-source message and no PASS or field-present wording. The existing resolver produces REVIEW / INSUFFICIENT_DATA.
- **Exact proposed behaviour for a VALID source with an absent, empty or whitespace-only extracted field:** Return `Raw.INDETERMINATE` / `EvidenceState.UNCERTAIN` / REVIEW / INSUFFICIENT_DATA. The current extraction model does not provide a separately verified negative observation proving that the printed field itself is blank; a missing extraction must not be promoted to a verified violation. Only a future explicit, provenance-backed “visually confirmed blank field” signal could justify a violation; none is proposed here.
- **Exact proposed behaviour for a VALID source with a non-empty field:** Return `Raw.SATISFIED` and propagate the field's normalized evidence state. Verified extraction may resolve to PASS / CONFIRMED_OK, but the message must say only that the name field was extracted from the supplied document. Provisional or uncertain extraction resolves to REVIEW / CANNOT_CONFIRM. A PASS here means field extraction only, not identity authentication, legal-name validation, Aadhaar-mobile linkage or e-KYC completion.
- **Multi-source behaviour:** If a rule names more than one source document, any absent, MISSING, unreadable or corrupted required source makes the rule indeterminate. A field found in another source must not produce a satisfied result for the full required source set.
- **Severity boundary:** Keep `max_severity: REVIEW`. The cap cannot substitute for correct raw/evidence semantics. Do not use a verified violation to represent an extraction gap.

**Required tests after approval (primitive-level and Subhadra packet-level):**

1. Source absent from packet: `Raw.INDETERMINATE`, evidence UNCERTAIN, `Status.REVIEW`, `INSUFFICIENT_DATA`; no PASS and no “field present” message.
2. Explicit document `status: MISSING`: same result as absent source; no `Raw.SATISFIED`.
3. UNREADABLE and CORRUPTED source documents: each returns indeterminate/uncertain and REVIEW / INSUFFICIENT_DATA; no PASS or FAIL.
4. VALID document with field key absent: indeterminate/uncertain and REVIEW / INSUFFICIENT_DATA.
5. VALID document with empty string and whitespace-only raw value: both indeterminate/uncertain and REVIEW / INSUFFICIENT_DATA; neither may be described as “present and non-empty.”
6. VALID document with non-empty verified field: satisfied/verified and PASS / CONFIRMED_OK; assert that the message is limited to successful extraction.
7. VALID document with non-empty provisional or uncertain field: satisfied with the weaker evidence state, then REVIEW / CANNOT_CONFIRM; it must not become PASS.
8. Multi-source case: if one required source is absent/unreadable while another source contains the field, the combined rule remains REVIEW / INSUFFICIENT_DATA.
9. **Shared-primitive cross-pack regression:** Before changing `field_present`, inventory every active or test pack in the repository whose rules invoke this shared primitive. Add or extend regression coverage for every affected pack, not only `odisha.subhadra`. Exercise the absent/MISSING source, UNREADABLE/CORRUPTED source, VALID source with absent/empty/whitespace-only field, and non-empty VERIFIED/PROVISIONAL/UNCERTAIN field cases wherever those states are relevant to the pack contract. Run each affected pack through its real pack-driven validator or packet-level test path, assert the expected raw/evidence/resolved outcomes, and verify that the shared change creates neither an unintended PASS nor an unintended FAIL in other packs. Preserve existing intended behaviour for packs not requiring the Subhadra-specific correction, or explicitly document and approve any intentional cross-pack behaviour change before implementation.

These are acceptance requirements for a later implementation change; they have not been added or run because implementation remains on hold. The cross-pack regression requirement is mandatory because `field_present` is shared engine behaviour; Subhadra-only tests are insufficient to establish safety for other pack consumers.
