## 2. Parameter-level verification matrix

Status vocabulary:
- **VERIFIED** — the cited official source expressly establishes the requirement or rule.
- **PARTIALLY VERIFIED** — the source establishes part of the proposition, but scope or operational interpretation remains unresolved.
- **UNVERIFIED** — no adequate authoritative evidence has been established for the specific proposition.
- **NOT AUTOMATABLE** — legal requirement may be verified, but the current DocuReady inputs/integrations cannot safely determine it.
- **DEFERRED** — deliberately not implemented pending trusted evidence, product-owner approval, or a suitable primitive.

**Reason-code compatibility clarification (24 November 2026):** The strings `TRANSITION_REQUIRES_YEAR_SCOPE` and `EXTERNAL_VERIFICATION_REQUIRED` used in earlier review wording are **illustrative issue labels only**. They are not members of the canonical `ReasonCode` enum in `src/docuready/domain/enums.py`, are not existing engine reason codes, and are not authorized additions. They must not be written to findings as reason codes. For the unresolved age-transition scope and unavailable external verification described in this matrix, use the existing contract: `Raw.INDETERMINATE` + `EvidenceState.UNCERTAIN` resolves to `Status.REVIEW` / `ReasonCode.INSUFFICIENT_DATA`. Where a different raw/evidence combination is actually produced, use the existing resolver truth table rather than inventing a label. No new enum value, resolver branch, or severity behaviour is proposed or authorized.

## 3. Specific rule-level review findings

### RULE-SUB-DOC-01 — Aadhaar document slot

- **Legal fact:** Aadhaar card/Aadhaar number in the applicant's own name is a verified scheme requirement (Gazette §5(a)(i); Guidelines §7(a)(i); SOP §2(f)).
- **Pre-correction primitive behaviour (historical):** Prior to `2024.1.1`, `eval_require_document()` returned `Raw.DOC_ABSENT` when the requested slot was absent, and the V2 resolver handled `Raw.DOC_ABSENT` before severity-cap processing to return `Status.MISSING` / `ReasonCode.DOC_ABSENT` (`Readiness.NOT_READY`). `max_severity: REVIEW` could not convert `Raw.DOC_ABSENT` to `REVIEW`, and `ReasonCode` has no `DIGITAL_EVIDENCE_NOT_SUPPLIED` value.
- **Approved decision and implementation (`2024.1.1`):** On 27 November 2026, the Product Owner confirmed Akriti's agreement with this source-review matrix and the Aadhaar-upload interpretation and authorized the correction. `RULE-SUB-DOC-01` has been removed from `packs/odisha.subhadra/pack.yaml` (`version: "2024.1.1"`), while `doc_slots.aadhaar_card.required: false` is retained. T3.3 final acceptance remains open.
- **Result when the digital scan is absent:** No standalone missing-Aadhaar-upload finding is emitted (`Status.MISSING` is not raised solely for an absent optional upload). Aadhaar-dependent rules (`RULE-SUB-FLD-01`, `RULE-SUB-AGE-01`, `RULE-SUB-NAME-01`) abstain via `Raw.INDETERMINATE` + `EvidenceState.UNCERTAIN` and resolve to `Status.REVIEW` / `ReasonCode.INSUFFICIENT_DATA`, yielding packet readiness `NEEDS_CHECKS` rather than `NOT_READY`.
- **Unreadable/corrupted scan:** Preserves `Raw.INDETERMINATE` / `EvidenceState.UNCERTAIN`, resolved to `REVIEW` / `INSUFFICIENT_DATA`; emits no statutory `FAIL` or `Status.MISSING`.
- **Applicant-facing explanation:** Any optional-upload reminder remains a non-finding UI/help-text state outside the rule resolver and does not invent a statutory status or reason code.
- **Physical possession remains distinct:** Aadhaar possession and Government e-KYC requirements remain distinct from DocuReady digital upload. Absence of a DocuReady scan cannot establish that the applicant lacks physical Aadhaar/Aadhaar number; conversely, an optional upload is not evidence that e-KYC or Aadhaar-mobile linkage has been completed.

### RULE-SUB-FLD-01 — applicant-name field presence

- **Pre-correction primitive behaviour (historical):** Previously in `eval_field_present()`, a missing source document or any non-`VALID` source document was skipped with `continue`, returning `Raw.SATISFIED` with `EvidenceState.UNCERTAIN` (or false `PASS` in multi-source rules) and a message that the mandatory field “is present and non-empty”; a `VALID` source with an absent/empty field returned `Raw.VIOLATED` / `EvidenceState.VERIFIED`.
- **Approved and implemented behaviour for an absent source:** Returns `Raw.INDETERMINATE`, `EvidenceState.UNCERTAIN`, identifies the unavailable source document in `documents_involved`, attaches no fabricated field evidence, and emits an explicit unavailable-source message. The existing resolver produces `Status.REVIEW` / `ReasonCode.INSUFFICIENT_DATA`.
- **Approved and implemented behaviour for a source marked MISSING:** Treated identically to an absent source: `Raw.INDETERMINATE` / `EvidenceState.UNCERTAIN` / `REVIEW` / `INSUFFICIENT_DATA`; no `Raw.SATISFIED`.
- **Approved and implemented behaviour for unreadable/corrupted/mismatched source:** Returns `Raw.INDETERMINATE` / `EvidenceState.UNCERTAIN` with an explicit unavailable-source message and no `PASS` or field-present wording. The existing resolver produces `REVIEW` / `INSUFFICIENT_DATA` while preserving any separate slot-mismatch finding.
- **Approved and implemented behaviour for a VALID source with an absent, empty or whitespace-only extracted field:** Returns `Raw.INDETERMINATE` / `EvidenceState.UNCERTAIN` / `REVIEW` / `INSUFFICIENT_DATA`. The current extraction model does not provide a separately verified negative observation proving that the printed field itself is blank; a missing extraction is not promoted to a verified violation.
- **Approved and implemented behaviour for a VALID source with a non-empty field:** Returns `Raw.SATISFIED` and propagates the field's normalized evidence state. Verified extraction resolves to `PASS` / `CONFIRMED_OK` (meaning field extraction only, not identity authentication or e-KYC completion). Provisional or uncertain extraction resolves to `REVIEW` / `CANNOT_CONFIRM`.
- **Multi-source and mixed-source behaviour:** If a rule names more than one source document, any absent, `MISSING`, unreadable, corrupted, mismatched, or unextracted/empty required source makes the rule `Raw.INDETERMINATE` / `EvidenceState.UNCERTAIN` (`REVIEW` / `INSUFFICIENT_DATA`). Genuine provenance from successfully extracted fields is preserved without fabricating provenance for absent sources.
- **Severity boundary:** `max_severity: REVIEW` retained on `RULE-SUB-FLD-01`; no new reason code, resolver branch, or severity shortcut was added.
